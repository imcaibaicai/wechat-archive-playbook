# 02 · 密钥机制：SQLCipher 4 与"用户自备密钥"边界

> 本篇是机制分析。本仓库**不提供、也不包含**任何从第三方进程中
> 自动提取密钥的代码；使用者需通过自己合法的渠道获得密钥后，
> 用本仓库的 `verify` / `decrypt` 子命令完成解密。这样划分的原因
> 见 USE_POLICY.md。

## 1. SQLCipher 4 的密钥派生（公开规范）

SQLCipher 是开源软件（BSD 许可证），其 4 版格式完全公开：

```
文件头 salt        : 16 字节随机值（每个分片库独立）
mac_salt           : salt 逐字节 XOR 0x3A
mac_key            : PBKDF2-HMAC-SHA512(key, mac_salt, rounds=2, dklen=32)
每页 reserve 区    : IV(16) + HMAC-SHA512(64) = 80 字节
页面加密           : AES-256-CBC，IV 取本页 reserve 区前 16 字节
HMAC 覆盖范围      : 页面前缀 + 页码（页面 1 附加 01 00 00 00）
```

页面 1 解密后的前 16 字节必为 `SQLite format 3\x00`——
这是校验密钥正确性的最快探针。`src/sqlcipher4.py` 的
`verify_key()` 先验 HMAC 再解密，避免用错密钥写出一堆垃圾文件。

## 2. 多分片库 = 多套密钥的映射方法

每个分片库有独立 salt，因此**单个密钥通常无法解开全部分库**。
实操中会得到一组（salt, key）对。建立映射的方法：

1. 对每个 `.db` 读文件头 16 字节得到 salt_hex（文件级指纹）；
2. 用手上的每个候选密钥对该库执行 HMAC 校验，命中即记录
   `salt_hex -> key`；
3. 之后按 salt 精确选用对应密钥解密，无需逐个试错。

`src/cli.py decrypt` 内部正是"对每库尝试所有候选密钥"的批量版本。

## 3. 密钥在宿主进程中的持有形态（机制说明）

为便于使用者判断"我手上的密钥是不是完整的"，这里客观描述
4.x 客户端持有密钥的机制（逆向社区已有大量公开分析，本仓库仅整理）：

- 客户端基于 WCDB 封装 SQLCipher，数据库密钥由内部
  `CipherConfig` 配置对象持有；
- 该对象除 32 字节原始密钥外，还携带 page_size、cipher_version
  等元信息（常见值 4096 / 4，可作为对象识别特征）；
- 密钥缓冲区在内存中**经过 XOR 类混淆**而非明文存放，直接搜
  `x'<hex>'` 明文字符串在 4.x 上已不可靠；
- 混淆使用的掩码与对象实例均可从进程内存中定位、还原——
  具体偏移随版本变化，本仓库不固化任何版本特定地址。

**给 Agent 的重要提醒**：任何"自动提取"行为都触及
OpenProcess/ReadProcessMemory 这类敏感 API，且偏移量随版本失效。
把它作为公开仓库的默认功能，会直接引来 DMCA takedown
（多个知名导出项目已在 2025 年因此删库）。本仓库因此只做
"给定密钥 -> 解密/导出"，把密钥获取留给使用者在自己机器上
自行解决。

## 4. 密钥的保存纪律

- 密钥等同明文数据：只写本地文件（如 `keys.txt`），并确保该文件
  被 `.gitignore` 排除；
- 不要把密钥、salt 映射表、解密产物提交进任何仓库；
- 导出完成后如需长期保留，优先保留解密库或 Markdown 归档，
  并置于同样的隐私保护之下。
