# 01 · 存储架构：数据在哪、长什么样

> 本篇描述 Windows 客户端 4.x 的本地存储结构。所有路径都位于当前用户
> Documents 下，属于用户自己的数据。

## 1. 目录结构

```
Documents/
└── xwechat_files/
    └── <账号目录>/
        └── db_storage/
            ├── contact/            # 联系人
            ├── session/            # 会话列表
            ├── message/            # 消息分片（核心）
            │   ├── message_0.db
            │   ├── message_1.db
            │   └── ... message_N.db
            ├── biz_message/        # 公众号 / 服务消息
            ├── media/              # 媒体索引
            ├── message_fts/        # 全文检索索引
            └── message_resource/   # 资源（图片/文件）索引
```

3.x 时代的路径是 `Documents\WeChat Files\<wxid>\Msg\MSG0.db`，
4.x 起整体迁移到 `xwechat_files\<账号目录>\db_storage\`，
由少量集中大库变为**模块化分库**。

## 2. 数据库文件头：加密形态识别

每个 `.db` 文件并非 SQLite 明文，而是 SQLCipher 4 加密容器：

| 偏移 | 长度 | 内容 |
|------|------|------|
| 0    | 16   | Salt（每个分片库独立，随机） |
| 16   | 4080 | 第 1 页加密数据 |
| 页尾 | 80   | reserve 区 = IV(16) + HMAC-SHA512(64) |

判断一个 `.db` 是不是加密容器：读前 16 字节，如果不是
`SQLite format 3\x00` 而是随机字节，即为加密库；其 hex 值就是该库的
salt，用作密钥匹配的指纹（见 02 篇）。

## 3. 消息内容：ZSTD 压缩

4.x 起消息正文字段普遍经过 **Zstandard** 压缩后入库，
压缩流以魔数 `\x28\xb5\x2f\xfd` 开头。解密得到明文 SQLite 后，
读取 `message_content` 字段仍需过一次 ZSTD 解压 + UTF-8 解码
（`src/content.py` 已封装）。非压缩内容（旧数据、部分系统消息）
原样解码即可。

## 4. 会话 -> 数据表映射

消息按会话分表存放，表名规则：

```
表名 = "Msg_" + md5(会话标识).hexdigest()
```

- 会话标识：对联系人的 wxid、群聊 id；文件传输助手固定为 `filehelper`
- 例：`md5("filehelper") = 9e20f478899dc29eb19741386f9343c8`
  → 表名 `Msg_9e20f478899dc29eb19741386f9343c8`
- 同一张表的数据**跨分片库分散存放**（message_0 ~ message_N 中都可能出现），
  导出时必须遍历所有分库合并查询

`session` / `contact` 库中的 `Name2Id` 映射表可用于把
`talker` 标识解析回可读的昵称/群名。

## 5. 消息表关键字段

| 字段 | 含义 |
|------|------|
| `local_id` | 库内自增消息 id |
| `create_time` | Unix 时间戳（秒） |
| `local_type` | 消息类型；1 = 纯文本 |
| `message_content` | 正文（可能 ZSTD 压缩）或 XML 载荷 |
| `talker` / 会话归属 | 由所在表决定 |

非文本消息（图片、文件、分享链接）正文多为 XML：
`<appmsg><title>..</title><des>..</des><url>..</url></appmsg>`，
`<img md5=".."/>` 为图片占位。`src/content.py` 的
`clean_message_content()` 负责把这些载荷还原为可读 Markdown。
