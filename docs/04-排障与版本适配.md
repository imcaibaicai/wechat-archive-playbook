# 04 · 排障与版本适配

## 常见失败与处理

| 现象 | 原因 | 处理 |
|------|------|------|
| `verify` 全部 mismatch | 密钥与库不对应；或库不属于 SQLCipher 4 格式 | 确认密钥来源；用 `01 篇` 的文件头特征复核格式 |
| 解密后文件打不开 | 用错密钥强行解密（HMAC 未过仍写盘） | `decrypt_db` 已内置 HMAC 前置校验，不会写出坏文件；若文件来自旧脚本，删除重来 |
| 文本乱码 | 漏了 ZSTD 解压或编码回退 | 走 `src/content.py` 的 `safe_decode()`（UTF-8 → GBK） |
| 表不存在 | md5 算错（标识含后缀/大小写差异）或数据在其它分片库 | 核对会话标识；遍历所有分片库再下结论 |
| 导出缺消息 | 只查了一个分片库 | 同一会话表跨库分散，`collect_messages()` 已合并全部分片 |
| 同秒消息互相覆盖 | 文件名冲突 | 已自动追加 `_N` 序号，检查是否用了旧脚本 |

## 版本差异速查（3.x → 4.x）

| 维度 | 3.x | 4.x |
|------|-----|-----|
| 进程位数 | 32 位 | 64 位 |
| UI 框架 | 自研 | Qt |
| 数据根目录 | `WeChat Files\<wxid>\Msg` | `xwechat_files\<账号目录>\db_storage` |
| 库组织 | `MSG0.db` 集中大库 | 模块化分片 `message_0..N.db` 等 |
| 加密 | SQLCipher 3 | SQLCipher 4（HMAC-SHA512） |
| 正文 | 明文/简单编码 | ZSTD 压缩为主 |
| 会话表 | 统一大表 + talkerId | `Msg_<md5(标识)>` 分表跨库 |

**适配新版本的通用方法**（不依赖任何硬编码偏移）：

1. 看文件头：16 字节 salt + 80 字节页尾 reserve，确认仍是
   SQLCipher 4 家族；若 reserve 布局变化，调整 `sqlcipher4.py`
   的 `RESERVE_SZ` 常量；
2. 看正文：抽样读 `message_content`，检查 ZSTD 魔数是否变化；
3. 看表名：对若干已知会话算 md5，用 `sqlite_master` 验证
   `Msg_<md5>` 规则是否仍成立；
4. 看密钥：`verify` 能过说明密钥形态未变；若全库 mismatch，
   再怀疑密钥获取方式过期（02 篇第 3 节的机制是否被修改）。

## 给后续 Agent 的建议

- 本仓库的 `src/` 与版本无关的部分是解密与解码算法；
  版本相关的只有"表名规则、目录布局、压缩魔数"三处，
  都在 docs 里有明确判定方法，按上面的四步重新核对即可；
- 不要把任何版本特定的内存地址、PID、绝对路径写进代码，
  那是旧脚本失效的根因。
